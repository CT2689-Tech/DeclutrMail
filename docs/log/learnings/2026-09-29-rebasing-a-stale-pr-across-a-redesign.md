## 2026-09-29 — Rebasing a stale PR across a redesign: find where the data moved, not just where the prop went

**Context:** Adopting PR #762 (first-cleanup nudge on Senders), open since 2026-09-21, and merging `origin/main` into it. Eight days of main included #765's "Apple-simple" redesign of `senders-screen.tsx`.

**Finding:** The merge conflicted on `summaryFailed`/`hasCompletedCleanup` prop wiring. Grep showed `summaryFailed` and the `summaryQuery` variable that fed it were gone from `origin/main` entirely — not moved, just deleted along with the honest-failure banner, as part of #765 dropping the whole "hero/KPI driven by a separate `/senders/summary` fetch" architecture (hero/KPI counts now come from `queryMeta` embedded in the list-query response). Taking origin/main's side naively would have left `hasCompletedCleanup` with no data source — a compiling-looking merge that silently always resolves to `undefined` (nudge permanently off). The fix was in `apps/web/src/features/senders/api/use-senders-summary.ts`'s own doc comment: `/senders/summary` is still called, just hoisted to `app-chrome-layout.tsx` for a nav badge, with a comment stating "the Senders screen reuses the same cache entry." Re-adding an unscoped `useSendersSummary({})` call in `SendersScreen` (matching that cache key) restored `hasCompletedCleanup` as a TanStack cache read, not a second network request. Separately, the PR's new component used a raw `<a>` for in-app navigation — the exact shape PR #820 (merged the same day) had just fixed across 7 marketing routes for a bundle-chunk leak. This file wasn't one of #820's targets (it already uses `next/link` elsewhere in the same feature dir), so the leak mechanism didn't apply here, but the convention drift was worth fixing anyway to match `observe-window-banner.tsx`'s sibling pattern.

**Rule (provisional):** When a merge conflict shows a variable/prop that simply vanished on `main` (not renamed at the conflict site), grep the WHOLE repo for its old identifier before deleting your side's reference to it — the data source likely moved to a different component, and the intended new call site is often documented in that dependency's own comments. Also: when adopting a stale PR, diff its new files against the day's other same-day merges for the exact defect SHAPE (not just the exact FILE) those merges just fixed.

**Distillation trigger:** promote to CLAUDE.md §3 (source-of-truth precedence / conflict resolution) if a second stale-PR rebase loses a feature's data source the same way.
