## 2026-09-26 — The lock-leak page fired about every 13 minutes on an info-level timing line
**PR:** #793 (https://github.com/CT2689-Tech/DeclutrMail/pull/793) fixes it; #765 added the line, and #509's alert took it in
**Caught by:** alert-history review during the stuck-mailbox starve test. The "Mailbox lock: leak or acquisition failure" policy held 240 alerts.
**What happened:** `setup-mailbox-lock-alert.sh` counts every `mailbox_lock.*` log kind by design: "a fifth added later is alerted on the day it ships". #765 (2026-09-24) added `mailbox_lock.slow_operation`, an info-level timing line, and from then the page opened about every 13 minutes. In the 24 hours to 2026-09-27 00:40Z, prod logged 431 `slow_operation` lines and 3 real `acquire_failed` lines. The 3 real acquisition failures reached the policy's email channel as more of the same page. The setup script only creates what is missing, so it could not have shipped a narrower filter anyway. Narrowing the filter then exposed a second gap: a failed lock-pool checkout or `lock_timeout` happened outside the only catch that logged `acquire_failed`, so it had paged only by accident, through the timing line.
**Correct approach:** Page on an enumerated list of failure kinds, and make every failure log one of them: `acquire_failed` now covers each stage of taking the lock. A test classifies every kind the code emits as page or no-page, and fails on one it has not classified.
**Rule:** An alert over a family of log kinds names the kinds that page. A new kind is classified before it ships, never enrolled by a prefix.
**Enforcement update:** `scripts/mailbox-lock-alert.test.mjs` reads every `mailbox_lock.*` kind in `apps/*/src` and `packages/*/src` and fails on an unclassified or unreadable one. `mailbox-action-lock.spec.ts` covers `acquire_failed` at each stage. The setup script verifies and converges the metric in place.
