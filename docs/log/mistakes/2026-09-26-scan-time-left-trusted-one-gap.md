## 2026-09-26 — The scan's time left trusted one gap between batches, and one gap can hold a pause
**PR:** TBD (feat/d109-sync-gate-progress-count)
**Caught by:** flow-completeness-auditor and an adversarial review, round 2 (a discrete-event simulation driving the real estimator); a third adversarial pass, round 3
**What happened:** A stall only restarted the estimate once a pace existed, so the first gap after any restart — mount, tab return, a retry — was taken as the pace, whatever it held. A 5-minute pause there showed "about 6 hr 35 min left" for 16 minutes of scan, and inflated the stall window so a later real stall kept a countdown for 15 minutes. Nineteen unit tests passed throughout: each encoded a scenario the author had imagined.
**Correct approach:** Show a time only once two gaps agree, and measure again from a batch that lands far faster than the pace so far (an earlier gap held a pause). Round 3 found the same rules also timed each *observed step*, so a failed read spanning several batches read as a pause; gaps are now judged per email, with the usual gap one batch (the smallest count step seen) at the average pace.
**Rule:** A rate estimate needs a second sample before it is shown: one sample cannot reveal that it is the outlier.
**Enforcement update:** estimator and hook tests, each red against a negative control (rebase, two-gap minimum, per-email gaps, hidden-tab reset, failed-read tolerance).
