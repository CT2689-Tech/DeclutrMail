## 2026-09-29 — `pnpm install --no-frozen-lockfile` left a stale specifier; plain `install` fixed it
**PR:** [#754](https://github.com/CT2689-Tech/DeclutrMail/pull/754) (dependency bump, `@google-cloud/kms` 5.7.0 → 6.2.1)
**Caught by:** CI (`Typecheck`, `Lint`, `Tests — API (1)/(2)` all failed with `ERR_PNPM_OUTDATED_LOCKFILE`), after push
**What happened:** Resolving a real `pnpm-lock.yaml` conflict (main's lockfile had drifted from #754's branch via 8 days of unrelated dependency churn), I ran `git checkout --theirs pnpm-lock.yaml` (main's lockfile, kms specifier still `^5.5.1`) then `pnpm install --no-frozen-lockfile` to layer the branch's `apps/api/package.json` change (`^6.2.0`) on top. The install succeeded and visibly added the new resolved package to the lockfile's top-level `packages:` table (confirmed via `git diff | grep kms`), so it looked fixed. It wasn't: the `importers` section's own `specifier`/`version` pair for `apps/api` stayed at `^5.5.1` / `5.7.0`, unchanged. Pushed anyway on the strength of a `git diff` grep that matched the wrong section. CI's `--frozen-lockfile` install (correctly) rejected the mismatch between `package.json` (`^6.2.0`) and the lockfile's recorded specifier (`^5.5.1`).
**Correct approach:** After any lockfile conflict resolution, verify the specific importer's `specifier`/`version` lines directly (`grep -A2 "'<pkg>':" pnpm-lock.yaml` under the right importer, or `pnpm why <pkg> --filter <workspace>`) — never infer correctness from a `packages:`-table diff alone, since that table can update independently of an importer's own recorded specifier. Separately: plain `pnpm install` (no flag) resynced the specifier correctly on retry where `--no-frozen-lockfile` had not. Not fully explained; treat the two as behaviorally different rather than interchangeable until proven otherwise.
**Rule:** After resolving any `pnpm-lock.yaml` conflict, grep the changed package's importer entry specifically and confirm `specifier` matches `package.json` before pushing — a `packages:`-table change is not proof the importer entry updated too.
**Enforcement update:** none (process discipline; no hook currently checks this pre-push, and a `--frozen-lockfile` dry-run pre-push hook would be the mechanical fix if this recurs).
