## 2026-09-26 — A new retry loop routed people through exits that answered in API JSON

**PR:** fix/d108-require-gmail-scope (Gmail scope check at the OAuth callback)
**Caught by:** flow-completeness-auditor + adversarial reviewer + usability-editor (pre-PR)
**What happened:** The Gmail check sent people back to Google in a loop: the /sign-in line, then "Continue with Google", then Google's screen again. Every other way that loop can end was already a dead end. Cancel on Google's screen during sign-in or when adding a mailbox fell through to a missing-code 400. A reused or expired code, a failed token-info lookup or an orchestrator failure was rethrown as a 500. A stale state cookie was a 400. A fifth quick retry within a minute hit the auth rate limit as a 429. All of these rendered the API's JSON error envelope as a full page on the API origin. `/connect-mailbox/start` did the same for any unexpected failure. Structural gates and unit tests (which call the handler directly and assert the throw) cannot see what a browser shows. The web side dropped results too. For someone who had not finished onboarding, a result sent to Settings or Triage never showed: the onboarding gate's bare `router.replace('/onboarding')` discarded the query, and Settings or the chrome could use it up first while the onboarding-state read was still in flight. Reproduced in a browser before fixing: `/settings?reconnect_result=…` → `/onboarding`, no message.
**Correct approach:** The OAuth browser routes get exit filters that extend `AllExceptionsFilter` and override only `respond()`, as `IconErrorFilter` already did. Every failure lands on /sign-in or Settings with a closed result, and the base filter's structured log and 5xx Sentry capture still run. Google's `access_denied` is handled in the handler and returns the person where they started. On the web, the result's consumers wait until onboarding state is known, the gate carries the closed result, and /onboarding shows it. Each exit was smoked through the running API and a real browser.
**Rule:** A route a browser navigates to must answer every failure with a page, and a result must survive every redirect between where it lands and where it is read; check both before sending more people through a flow.
**Enforcement update:** HTTP-level filter specs (a rejection before the handler runs still redirects), a controller metadata test that both routes carry their filter, controller specs for cancel and other Google errors, and web specs for the gate carrying each result and both consumers waiting; each negative-controlled. None to hooks.
