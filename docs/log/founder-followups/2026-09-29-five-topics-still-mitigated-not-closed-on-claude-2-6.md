### 2026-09-29 — CLAUDE.md §2.6: 5 live outbox topics are mitigated, not closed — the claim/lease redesign is still a real, separate, open decision
**Source:** PR #826 (https://github.com/CT2689-Tech/DeclutrMail/pull/826); architecture-guardian review
**Why:** #826 bounds every outbox consumer call with `consumerTimeoutMs` (default 30s) plus an orphan guard, applying to the 5 topics whose consumer makes a network call inside the dispatcher's open claim transaction: `autopilot.rule_activated`, `mailbox.sync_ready`, `triage.score_run_completed` (all via `enqueueAutopilotApply`), `mailbox.reconnect_required`, and `mailbox.sync_failed` (via `enqueueEmailSend`). This is a real, adversarially-reviewed improvement over the ad-hoc 5s wrapper #807 originally added for a 6th topic (`mailbox.non_mail_purged`) — a hung call now fails within a known bound instead of hanging forever.

**Correction 2026-09-29 (round-3 review, same day):** the "(as of this PR's fix round) a genuinely-stuck row eventually reaches `failed` + Sentry instead of retrying silently forever" claim above was wrong when written, and stayed wrong through round 2. The `timeoutStuckCeilingMs` check only ran inside the per-row catch block that fires when a row IS reclaimed and times out AGAIN — but a key stays orphan-guarded (and its row stays excluded from the claim query entirely) for exactly as long as the original abandoned call has not settled. A call that truly never settles (a sustained outage, not one that eventually answers late) is therefore never reclaimed, never re-times-out, and so never reached that check at all — the row sat `pending` forever with zero Sentry signal, the exact "guard that cannot fail" shape CLAUDE.md §8 warns about. Fixed round-3 (`escalateStuckOrphans` in `outbox-dispatcher.worker.ts`, run every tick independently of whether a new timeout occurs): now a genuinely-stuck row does eventually reach `failed` + Sentry, verified with a test using a consumer that never resolves its promise even once (not the repeated-real-timeout shape the original streak test covers).

Also correcting the 6th-topic mechanics: #807's own local 5s `withPublishTimeout` was removed in the same round-3 pass, not kept — it was found to silently defeat the orphan guard for that topic specifically (an inner bound that can fire before the dispatcher's own settles the consumer's promise early, so the orphan tracker sees an already-settled promise and clears it immediately while the real call keeps running untracked). All 6 topics now share exactly ONE bound, `consumerTimeoutMs` — there is no more per-topic `PUBLISH_TIMEOUT_MS` special case. See `docs/log/founder-followups/2026-09-28-waive-or-block-outbox-queue-in-transaction.md`'s final correction for the full account.

It does **NOT** close CLAUDE.md §2.6 for any of these topics. The rule's own words are "No network call, queue publish, or session-scoped Postgres primitive inside an open transaction" — and the network call still runs inside the transaction for all 6 topics, for up to `consumerTimeoutMs` per row, and up to `claimBatchSize * consumerTimeoutMs` if an entire batch hits the same outage. Nothing in this PR moves the call outside the transaction. Do not read "#826 merged" as "the §2.6 exposure is fixed" anywhere in the codebase, a PR body, or a founder conversation — it should read "mitigated," same as #807's own entries on this topic already say for the 6th.

**How:** This is a status record, not an action request today — but it names the actual open decision so it doesn't get silently assumed-closed later (the exact mistake #807's and #826's own docs already corrected once each — see `docs/log/founder-followups/2026-09-28-waive-or-block-outbox-queue-in-transaction.md` and `docs/log/mistakes/2026-09-28-outbox-consumer-publishes-inside-the-claim-transaction.md`). The founder's real choice, whenever it's worth revisiting:
1. **Leave it mitigated.** Every registered consumer's network call is now bounded and orphan-guarded, adversarially reviewed, with an eventual-failure ceiling. This is a materially safer state than before #826, and may be an acceptable permanent posture given none of these 6 topics currently see production load (per #807's own entry, `mailbox.non_mail_purged` has no publisher yet; the other 5 have shipped but at effectively zero volume pre-launch).
2. **Fund the redesign.** Actually closing §2.6 needs the dispatcher's claim/commit boundary redesigned: commit the row's claim (and its bookkeeping) BEFORE invoking the consumer, using a lease/visibility-timeout scheme (a `claimed_by`/`claimed_until` column, or equivalent) instead of holding the `FOR UPDATE` lock across the consumer call. This is why the row lock currently buys "a crash reverts the row to `pending` for free" — a lease scheme has to re-derive that guarantee itself (an expired lease releases the row), and is a bigger, cross-cutting change to `OutboxDispatcherWorker` and every registered consumer's assumptions, not a small follow-up.
**Verifies by:** No automated signal — this is a standing decision record. It resolves when either (a) a future PR implements the lease/visibility-timeout redesign and a gate re-run confirms §2.6 is genuinely satisfied (not just mitigated), or (b) the founder explicitly accepts the mitigated posture as permanent and this entry is marked Skipped with that reasoning.
