**Correction 2026-09-29 (after #807 merged):** the "once #826 merges, #807's local 5s timeout is redundant — revisit removing it" line above is wrong, not just optimistic. **Resolved 2026-09-29 (the fix round above landed):** #826's fix round is done. `rescore-senders.ts`'s `withPublishTimeout` now rejects with `OutboxConsumerTimeoutError`, the SAME branded class `OutboxDispatcherWorker`'s own `consumerTimeoutMs` bound throws (identity-checked via `instanceof`, not a `.name` string — a same-named-but-different `TimeoutError` from this codebase's own Gmail/BIMI/billing `AbortSignal.timeout()` clients was a second reason `.name` matching was unsafe). **Correction 2026-09-29 (round-3 architecture-guardian review, same day):** the "kept, not removed... strictly better" decision directly above was wrong, verified live. Branding the class fixed WHETHER a timeout is recognized correctly, but it did not fix WHEN the two bounds race: #807's inner 5s timer can still fire BEFORE the dispatcher's own `consumerTimeoutMs` (30s default), which means it settles (rejects) `rescoreSenders`'s OWN returned promise early — the SAME promise `OutboxDispatcherWorker.trackOrphan` tracks. Tracking an already-settled promise is a no-op: its `.then(clear, clear)` fires on the very next microtask, deleting the orphan-guard entry almost immediately, while the real, abandoned `addBulk` call keeps running for real, completely untracked. The very next tick then happily re-claims and re-invokes `rescoreSenders` for the same mailbox while the first call's publish is still in flight — silently defeating the exact guard #826 exists to provide, for this one consumer. "Strictly better" was never true once the orphan-tracking interaction is accounted for, not just optimistic. **Fix:** removed #807's local 5s timeout entirely. The dispatcher's own `consumerTimeoutMs` is now the ONLY bound for this consumer, so there is nothing left to race early — single source of truth, per CLAUDE.md's simplicity-first principle, and this topic (`mailbox.non_mail_purged`) still has no producer in prod (PR #791 has not merged), so nothing observed this defeat in practice. The test this entry originally cited (`rescore-senders.test.ts`'s "rejects with the SAME branded timeout...") is removed along with the code it asserted; the composed behavior is now proven end-to-end by `outbox-dispatcher.worker.test.ts`'s "rescoreSenders composed with the real dispatcher" test, which runs the real function AS the dispatcher's consumer through a real tick — the isolated unit test this entry originally relied on could not see this interaction, which is how it hid for two rounds.

Also corrected here: the same paragraph above claimed "a PERMANENTLY-stuck event still eventually fails and reports to Sentry" as an established fact of #826's `timeoutStuckCeilingMs`. That was ALSO wrong at the time it was written — see `docs/log/founder-followups/2026-09-29-five-topics-still-mitigated-not-closed-on-claude-2-6.md` for the full correction; the short version is that the ceiling check only ran when a row was reclaimed and timed out again, so a call that never settles at all (excluded from every claim) never reached it.
