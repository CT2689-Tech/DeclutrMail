### 2026-11-18 — A retried bulk Unsubscribe records each email-only sender twice

**Source:** independent review of the MCP connector's apply path on [CT2689-Tech/DeclutrMail#1209](https://github.com/CT2689-Tech/DeclutrMail/pull/1209). Not caused by that PR and not fixed in it.
**Why:** `ActionsService.enqueueBulkUnsubscribe` dedups its one-click rows on the request's idempotency key, but the loop that records senders who unsubscribe by email (`manual`) has no key. When a bulk Unsubscribe is sent again with the same key — a network retry from the web app, or the connector retrying after the queue refused a job — every email-only sender in the selection gets a second `unsubscribe_action_required` Activity row and a second outbox event. No mail moves and no request is sent twice; the one-click half stays exactly-once. Reproduced in the review with one confirmation and one retry (probe: a preview for two one-click senders and one mailto sender, confirm while the queue fails, then retry: 2 rows where 1 is expected). Checked on this branch 2026-11-18; the web route `POST /api/actions` with a `senders` selector and an `unsubscribe` primary reaches the same code.
**How:** decide whether to key the manual rows the way the one-click rows are keyed (for example on `unsub:<key>-<senderId>`), so a replay finds them. It was left out of the connector PR because it changes the unsubscribe pipeline for the web app too, and that deserves its own review. The connector already stops two requests from running the same confirmed preview at once; this is only the retry-after-failure case.
**Verifies by:** a test that sends the same bulk Unsubscribe twice with one idempotency key, with a mailto sender in the selection, and finds one `unsubscribe_action_required` row for it.
**Status:** Open
