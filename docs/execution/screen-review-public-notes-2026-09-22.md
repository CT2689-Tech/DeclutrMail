## Priority findings

1. **Correct the Screener promise before polishing it.** `/how-it-works` says the Screener collects new senders “instead of dropping them straight in your inbox” (`app/(marketing)/how-it-works/page.tsx:125`). This contradicts the review-only model explicitly documented in `features/marketing/screener-truth.test.ts:1`: email still arrives in Gmail. Say it lists unfamiliar senders for review while delivery continues. That test excludes inline JSX, so a passing truth gate does not cover this paragraph.
2. **Correct the simulator's storage lesson.** `features/marketing/inbox-simulator/inbox-simulator-screen.tsx:159–168` says everything “archived or unsubscribed” left the inbox and calls Delete the action that “actually clears space.” Unsubscribe alone moves nothing; Delete moves to Trash and does not immediately reduce storage. The storage guide already explains the correct distinction (`learn/how-to-content.ts:393–405`). Preserve its explicit distinction in step 4 and completion copy. This is a teaching inconsistency, not a request to add storage estimation.
3. **Correct the delete guide's recovery instructions.** `learn/how-to-content.ts:253–257` says the recovery note should attribute the roughly 30-day window to “Gmail Trash, not DeclutrMail.” Production and `product-story/diagrams.tsx:190` also offer Activity Undo for Delete. Explain both separately. The same guide says Delete is behind a full action menu (`:240,250`), but sender inspector has an explicit Delete action; use surface-neutral instructions.
4. **Scope universal preview promises to mail-moving actions.** `/how-it-works` “Preview before anything changes” (`page.tsx:96–101`) and `/methodology` “Nothing changes until the preview loads” (`page.tsx:121–125`) overgeneralize. Keep is an inline decision, and enabled automation subsequently acts without individual confirmation. Comparison content already says this correctly (`comparison-data.ts:140–143`). Use that precise boundary throughout; retain existing automation explanation.
5. **Teach the actual entry experience.** The public demo is an interactive **Triage** sample, with guided batch/action/rule steps and production sheet components (`inbox-simulator-screen.tsx:830–867,972–1011`). The revamped app initially presents Overview and a grouped navigation with a sender inspector. This is not a broken demo; add a short Overview → Clean up → Senders orientation or explicitly label it “Try a daily review.” Do not replace production action sheets with decorative imitation controls.
6. **Reduce consent-entry inconsistency.** `/sign-in` is a good explicit permissions checkpoint, but global Sign in and Start free both bypass it for direct OAuth (`public-shell.tsx:90–110`; `auth-entry.tsx:26–105`). Hero/article/story CTAs include a scope disclosure; global header CTAs do not carry that nearby context. Decide one deliberate convention: consistently direct newcomers through the checkpoint, or keep direct OAuth and expose a concise adjacent permission link. This is a design opportunity, not a broken OAuth claim; direct OAuth is currently intentional.
7. **Close the recovery documentation gap.** `/answers/how-undo-works-for-gmail-cleanup` still describes Triage's tray and says not to assume a global tray (`answer-content.ts:255`). The current shell supplies recovery on mailbox-backed routes, excluding account surfaces. Update to “Activity is always the dependable destination; recent actions are also available across mailbox screens.” Avoid saying every route has recovery controls.

Source prefixes in this document are under `apps/web/src/` unless stated otherwise. Existing findings may predate this visual revamp; these are current experience issues, not all newly introduced regressions.
