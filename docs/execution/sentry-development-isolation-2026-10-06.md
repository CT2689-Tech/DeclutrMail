# Development Sentry isolation — launch repair

Owner and integration owner: Assess production launch readiness. Isolated branch:
`codex/sentry-development-isolation`, based on current main `796b8e7b`.
The existing core, performance, and launch-holds chats were stopped at inventory;
the only open PR was an unrelated dependency update. This repair owns Sentry
startup policy in the web browser, Next Node/edge, and API/worker bootstrap, the
shared observability policy, corresponding regression tests, and env documentation.
No dependency, database, billing, Gmail, or deployment configuration changes.

The complete story is optional error reporting: an application starts, an error
occurs, reporting either stays local or initializes the configured SDK, and the
product continues even if telemetry fails. All callers retain existing privacy
scrubbing. The user-facing outcome is the same working application; the operational
outcome is production monitoring capacity preserved during local development.

The October 6 investigation found 2,023 development issue events within the
September 21–October 6 window, about 39% of recorded volume. The retained sample
was a handled triage summary TypeError. This is a confirmed quota contributor;
the original network failure and workstation are not established. The current
startup gates check only DSN presence, so a configured development DSN initializes
Sentry and can consume the production organization's allowance.

The browser uses `NEXT_PUBLIC_VERCEL_ENV`, then `NODE_ENV`; Next Node/edge uses
`VERCEL_ENV`, then `NODE_ENV`; the API/worker uses `NODE_ENV`. Development opt-in
will be `NEXT_PUBLIC_SENTRY_DEV_ENABLED=true` for browser capture and
`SENTRY_DEV_ENABLED=true` for server capture. Use a separate development Sentry
organization/DSN for this opt-in: another project in the production organization
still shares its allowance. Production and preview behavior remain unchanged.

Payments, quota purchases, OAuth grants, mailbox mutations, notification sends,
and deletion/expiry verification are excluded. No production event is intentionally
generated by this rehearsal. The webhook pool-starvation incident, exact held-client
cause, production alert receipt, source maps, and broader functional launch checks
remain open; isolating development telemetry does not prove they are repaired.
