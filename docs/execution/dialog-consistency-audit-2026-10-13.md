# Dialog and Details consistency audit — 2026-10-13

## Flow contract and ownership

The user wants consistent pop-ups and dialogs across the app, including the Details inside them. Entry points include action previews, Activity filters/support/recovery, mailbox controls, Home cleanup, keyboard help and contextual help. Scope includes billing dialog presentation, but excludes purchases, plan changes, provider writes, account/data deletion and consent changes.

The complete UI story is open → understand the decision → optionally disclose supporting facts → cancel or hand off confirmation → return focus to the entry point. Existing confirmation eligibility, consequences, initial focus, busy locks, privacy defaults and typed acknowledgements remain authoritative. Terminal Gmail/billing outcomes are outside this presentation audit.

Integration owner: Codex, isolated c970 worktree, branch `codex/dialog-consistency`, fresh base `d0362669a`. Shared ownership: native disclosure and dialog layout primitives, their consumers and visual references. No PR dependency. Open #1037 overlaps Unsubscribe safety; its dispatch changes are excluded. Existing local authenticated data is an isolated development database copy; committed evidence uses fictional data only.

## Design plan, reviewed before implementation

Reuse the current frozen palette: background `#f6f2eb`, surface `#fffcf8`, ink `#2d2630`, primary `#59415f`, warning `#b45309`, danger `#a12525`. Keep Geist, the existing type/spacing/radius/motion tokens and semantic action colors.

Modal layout: a centered desktop panel and phone bottom sheet, with a left-aligned scrolling body and persistent footer. Action previews retain their existing centered composition; a support form needs a readable left-aligned body. Supporting Details use the same full-width native 44px header, trailing chevron, visible focus, wrapping text and flat expanded well. Contextual labels identify technical diagnostics and data inventories. Important consequences, privacy choices and confirmation inputs stay outside Details.

This plan fits DeclutrMail's existing decision surfaces: no new palette, cards inside cards, or decorative labels. Anchored menus/help and inline consent are meaningful separate patterns. Independent source critique agreed with shared Disclosure and presentational DialogFrame reuse; the frame must retain caller-owned focus and dismissal policy.

## Verification

Their file headers record consumers and D210 story coverage. The frame owns layout only; callers retain focus, confirmation and busy policy.

Regressions exercise Cancel's native Enter behavior, help ownership above an alertdialog, busy dismissal/focus transitions, and page shortcut suppression. Four initial behavior cases fail on the old components, the focus transition fails on the old hook, and five keyboard ownership cases fail on the old guards. In particular, Screener's native summary Enter/Escape preserves its inline decision and makes no POST; Triage ArrowRight preserves the sender; modal K cannot dispatch Keep behind a preview.

Browser checks use fictional Storybook data in the built-in browser. At 320×568, keyboard help, support, mailbox inventories, recovery, Home, mobile filters and upgrades have no page-wide horizontal overflow; long forms scroll and footer actions stay reachable. A long account title and 29-category inventory wrap. Native Details remain keyboard operable and focusable; headers are at least 44px, expanding to 55–56px for long labels. Busy recovery keeps focus on the panel through Tab/Shift+Tab. Dark mode wraps a long technical identifier with readable foreground. At 1280×800, long-dialog content scrolls inside a 520px panel with its footer ending at 784px and the Details header remaining 44px.

Billing cancellation and account deletion use the existing PreviewSheet; essential period-end, waiver, consequences and acknowledgements remain visible. Inline Triage Details retain their selected scope facts. These are presentation checks using fixtures, not purchases or deletions.
