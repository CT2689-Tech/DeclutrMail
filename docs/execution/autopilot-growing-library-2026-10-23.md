# Autopilot sender rules: implementation and verification

The founder approved Growing library and searchable sender selection, then requested production implementation on 2026-10-23. This authorizes the bounded sender-list builder described here, superseding the earlier preset-only UI deferral. Existing presets and their modes remain available. Root owns integration; API, worker, and web contributors use isolated branches. No real mailbox mutation is used for development evidence.

## Flow contract

User selects known senders from the active owned mailbox, names the rule, chooses Archive or Delete, Inbox or (Delete only) Inbox plus archived, and any age or older than 30/90/180 days. Creation and edits persist configuration only. Custom rules are approval-first; they never become unattended Active rules. Existing mailbox metadata supplies counts without Gmail or model calls.

One bounded list read provides rule summaries. Sender search is paginated and scoped to the mailbox; names and email addresses are data, never instructions. Protected senders remain excluded. Preview captures one five-minute, mailbox/rule/version-scoped snapshot of eligible message identifiers, action and scope. A cleanup may exclude selected senders or override its action/scope without changing the saved rule. Confirmation uses only the server-issued snapshot; clients cannot supply execution identifiers.

Confirmation creates one existing label-action job per sender, grouped under the first action ID. Save moves no email. An edit, retirement, account change or expiry cannot widen prior consent. Workers recheck eligibility before a first request, preserve frozen IDs for retries, and use the current Activity/Undo/recovery pipeline. Per-mailbox mutual exclusion and busy guards prevent conflicting simultaneous cleanups. Overlapping rule counts refresh after actions.

Custom rules are bounded to 50 per mailbox, 100 selected senders per rule and 5,000 emails per cleanup preview. A larger eligible set is described explicitly and continues through another reviewed cleanup. Sender search pages contain at most 25 rows. No general condition language, body processing, category prediction, payment changes or new OAuth scopes are included.

## Release status and limits

Implementation is local and independently reviewed. PR #1104 is open. Required CI, merge, migrations, deployment and authenticated production checks remain separate release gates. The production migrations require founder approval under CLAUDE.md stop conditions before merge triggers the existing migration/deployment workflows. No production serving-state or usage result is claimed by local evidence.

Custom rules stay approval-first. More complex condition builders, unattended custom Delete, predictive personalization and live-provider mutation testing are outside this launch scope. Scalar rule-change events use the existing consent gate; no message content, sender identity, rule name or token is added to analytics. No recurring monitor or paid service is created.

## Rollout and recovery compatibility

The client shares one mailbox-scoped sender-rule query. An exact HTTP 404 temporarily shows the complete existing preset screen and probes every 15 seconds; other failures retain an actionable library error. A successful response does not poll. Preset dialogs and in-flight mutations remain mounted through recovery, the disclosure stays open, and keyboard focus returns to a visible control or the preset heading. Global Pause all covers custom and preset rules, including disabled but non-paused presets. Retained legacy previews use all-rules wording while completeness is unknown, adopt the complete custom+preset list on idle recovery, and pin displayed scope after dispatch until completion or error. It refreshes both summary caches while preserving open frozen cleanup previews. The library registers the standard screen help, and existing preset journeys open its disclosure before exercising their original controls.

The existing release workflow waits for successful required CI and migration application, deploys and verifies the worker before promoting API producers, and does not require a workflow change here. The frontend tolerates an older API while that rollout completes. An older worker does not implement the new sender-rule guards: disable custom writes and drain all sender-rule jobs before considering a worker rollback. After custom rows exist, prefer a forward fix or retain the new preset filtering and worker compatibility; do not blindly revert the entire API/worker to the previous baseline. Database rollback deliberately refuses custom-row loss.

The initial PR run exposed four failures: the copy glossary, SQL timestamp-name guard, the cache-inventory expected-key list, and preset browser readiness after the library layout changed. Their causes are corrected without changing guard baselines, weakening the browser assertions, or bypassing checks. A fresh exact-head CI run is required; the initial failed run is not release evidence.
