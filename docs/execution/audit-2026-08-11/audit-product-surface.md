## 1. Headline

**16 app screens. 0 are complete against all nine states — but only 4 have a screen-specific gap.**

Two gaps are **systemic**, not per-screen, and they account for most of the ❌ cells:

| Systemic gap                                    | Reach                        | Evidence                                                                                                                                                                                                                                                                                                                                                             |
| ----------------------------------------------- | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`offline` is unimplemented product-wide**     | 16/16 screens                | Zero `navigator.onLine`, zero `online`/`offline` listeners, zero offline UI in `apps/web/src` + `packages/shared/src`. The D211 inventory self-declares `offline: {status:'todo'}` on 12 screens (`packages/shared/src/edge-states/inventory.ts`) and quietly sets `required: false` on every one, so nothing fails CI.                                              |
| **`sync in progress` has no in-screen surface** | 13/13 mailbox-backed screens | `meHasSyncingMailbox` (`apps/web/src/features/auth/api/use-me.ts:81`) has exactly one consumer — its own poll interval at `:121`. Sync state renders only in the account menu (`features/mailboxes/account-menu.tsx:312`), Settings → Mailboxes (`features/settings/settings-index/mailboxes-card.tsx:173-191`) and the onboarding gate. No feature screen reads it. |

Setting those aside: **11 of 16 screens are complete**, **5 carry a screen-specific gap** — `/senders` (two, one of which discards a loaded list), `/settings/privacy` (no loading/error branch; asserts a free-tier undo window when the plan read fails), `/screener` (upgrade path bypasses the D117 single-checkout funnel), `/admin/security` (orphan route, and unreachable with zero mailboxes), and `/settings/senders` shares the senders sync-lie.

**The three worth fixing first:** F-01 (a background refetch failure throws away the user's loaded senders list and selection), F-02 (an empty state whose only button leads to a screen with no buttons), F-19 (the trust page understates undo retention for paying users when a read fails).

**What is genuinely strong** — worth stating, because it narrows where to look:

- **Invariant 2 (read guard 4xx ≠ retry) holds everywhere.** `retryTransientOnly` (`apps/web/src/lib/api/retry.ts:11-14`) is the global default (`lib/query-client.ts:60`). I enumerated all 14 per-query `retry:` overrides — every one is `retry: false` or `retryUnless4xx` (`features/senders/api/retry.ts:21`). Exactly one deviation, low-impact (§4).
- **Invariant 1 (scope change ⇒ reset scoped cache) holds at every transition** (§4).
- The no-active-mailbox dead end from the 2026-05-28 session is **fixed and thorough** — `features/mailboxes/no-active-mailbox.tsx` offers per-mailbox reconnect, connect-another, Manage account, Billing and Sign out (`:132-269`).
- Every route has an error boundary with `reset()` **and** an escape link to a different route (`components/route-error-screen.tsx:44`). Nested settings routes inherit `app/(app)/settings/error.tsx` per App Router cascade — not a gap.
- D226 preview is wired on every destructive path I traced: triage, senders, screener (`features/screener/screener-screen.tsx:266` — "Preview confirm — the only place the decide mutation fires"), brief.

## 4. The two invariants

### Invariant 1 — scope change ⇒ reset scoped cache. **HOLDS.**

Every path that changes the server-resolved active mailbox is covered:

| transition                          | site                                                           | reset                                                                                           |
| ----------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Switch mailbox                      | `features/mailboxes/api/use-set-active-mailbox.ts:22`          | ✅ `onSuccess: () => resetMailboxScopedCache(qc)`                                               |
| Disconnect                          | `features/mailboxes/api/use-disconnect-mailbox.ts:26`          | ✅                                                                                              |
| Delete indexed data                 | `features/mailboxes/api/use-delete-mailbox-indexed-data.ts:27` | ✅                                                                                              |
| Onboarding protection review        | `features/onboarding/step-protection-review.tsx:117`           | ✅                                                                                              |
| Connect / reconnect / reactivate    | `features/mailboxes/connect-mailbox-url.ts:21,38`              | ✅ by construction — `window.location.assign` is a full-page nav, so the QueryClient is rebuilt |
| **Any mutation that 409s on scope** | `lib/query-client.ts:45-47`                                    | ✅ global `MutationCache.onError` safety net                                                    |

`resetMailboxScopedCache` itself is correct — a bare filterless `invalidateQueries()`, with an explicit comment on why `clear()` was the original 2026-05-28 bug (`features/mailboxes/api/reset-mailbox-cache.ts:16-27`).

**One hole:** the safety net is on `MutationCache` only. There is **no `QueryCache.onError` equivalent**, so a _read_ that 409s on scope does not reset the cache or re-derive the shell. That is F-05.

### Invariant 2 — a read guard's 4xx is a designed state, never a retry. **HOLDS.**

- Global default: `retry: retryTransientOnly` (`lib/query-client.ts:60`), which returns `false` for any 400–499 (`lib/api/retry.ts:12`).
- I enumerated **all 14** per-query `retry:` overrides in `apps/web/src`. Thirteen are `retry: false` or `retryUnless4xx` (`features/senders/api/retry.ts:21-27`, applied to all four sender-detail panes after the 12-retry storm of 2026-06-06). None widens retry onto a 4xx.
- **The one deviation:** `features/auth/api/use-me.ts:115-118` — `if (401) return false; return failureCount < 2`. A **non-401 4xx on `/api/auth/me` retries twice.** `/api/auth/me` is `JwtGuard`-only (not `CurrentMailboxGuard`), so a scope 409 is not reachable there; the practical exposure is a 403. Low severity, but it is the only override in the app that does not follow the rule as written.
