## Measure before sizing or moving

Run `node scripts/probe-db-latency.mjs` from the process location under comparison with `DATABASE_URL` supplied through the existing secret/environment mechanism. Do not place credentials on the command line or attach environment files. The probe uses one dedicated connection, 20 sequential `EXPLAIN (ANALYZE, FORMAT JSON) SELECT 1` queries, a 5s statement timeout, and a read-only connection default. It neither generates load nor queries customer tables.

- `connectAndCheckoutMs` includes initial connection/TLS/auth/pooler checkout. Because this is a dedicated one-connection probe, it is **not** production application's pool wait.
- `roundTrip` measures a held client's roundtrip, including driver, network, pooler and server work.
- `serverPlanning` / `serverExecution` are PostgreSQL's timing for that trivial query.
- `outsideServer` is roundtrip less reported planning/execution, clamped to zero. It includes network, driver, scheduling, serialization and pooler overhead; do not label it pure network time.
- Compare independent API-region and Oregon runs with timestamps and matching database endpoint. Never compare workstation samples with production route percentiles.

Actual local smoke (loopback Postgres, 20 samples): checkout 25.86ms; roundtrip p50 0.235ms / p95 0.470ms; server execution p50 0.003ms / p95 0.007ms. This verifies the tool against PostgreSQL; it says nothing about current production latency.

After restoring gcloud access, export bounded `http.request` logs for an agreed observation window and run `node scripts/summarize-performance.mjs <private-log-file>`. Keep raw logs private; use summarized route-template/timing output for reports. Obtain Cloud Run request concurrency, instance count, CPU/memory utilization, request latency and 5xx during the same window. Correlate read-operation timings, PostgreSQL query-plan timings and the dedicated probe; do not subtract overlapping parallel operation durations from total request duration. Direct API pool-wait telemetry is still absent: add driver-supported checkout instrumentation only after validating the driver's lifecycle rather than reporting the probe's checkout as application contention.

Pool budget must account for API max instances, worker main/lock/cron pools, revision overlap during deploys, pooler limits, migrations and platform reserved connections. API `3 × 10` clients alone is not the server-wide connection budget. Raising the pool without observing waits may increase DB contention. Leave the current limits in place pending the above measurements.

## API region cutover proposal and rollback

1. Record the serving revision/image digest, API domain mapping/DNS records and TTL, certificate status, all runtime settings and secret **references**, service identity/IAM, pool budget and the previous hour's route latency/error baseline. Identify whether DNS mapping or a load balancer owns routing. Region change must not silently create a second active scheduled worker.
2. Provision an API-only candidate in `us-west1` with the same verified immutable image and equivalent configuration. Keep current `us-central1` API serving. Plan temporary warm-instance cost and shared DB client headroom explicitly. Preserve the canonical public API hostname, OAuth redirect URI, cookie domain, webhook audiences, CORS and KMS identity. The KMS key remains in `us-central1`; measure its extra cross-region latency.
3. Validate candidate readiness and authenticated current-count contract using a controlled account, then time the same list/detail routes, auth refresh and permitted read-only action previews. Run the DB probe from the candidate location with approved runtime credentials. Compare at least 100 representative route requests per condition; include sample counts and mailbox size classes without mailbox identifiers.
4. Prepare domain/certificate validation before routing traffic. If the current mapping cannot coexist across regions, document the exact mapping/DNS handoff and certificate issuance window first; do not assume a DNS switch alone is safe. Keep the previous mapping/revision recoverable. Any security configuration changes require their own review.
5. After approval of the concrete route/domain plan, cut over and observe route p95, error rate, auth/callback failures, webhook verification, worker lag and database connections against baseline. Suggested rollback triggers: persistent auth/webhook errors, 5xx above 1% over 5 minutes, or p95 more than 20% worse over a comparable sample. These are proposed gates, not measured results or already-configured alerts.
6. Roll back routing/domain mapping to the recorded central API and verify certificate, readiness, authenticated counts and auth refresh. Keep the old API warm through DNS propagation and a successful observation window. Region cutover has no data migration; both revisions use the same database. Do not delete the previous service until rollback is no longer needed.

## API-first release contract procedure

For an additive API field, merge/deploy the API first, wait for the **serving** revision, run the authenticated smoke against the canonical production host, then merge the dependent UI. If API and UI are in one change, hold web promotion until the smoke passes using the hosting platform's existing release controls; GitHub CI green alone is insufficient. Do not assume the current independent auto-deploys enforce this order.

Use a short-lived controlled session and an existing sender in its active mailbox. Place the full Cookie header value in a private mode-0600 file outside the repository. Set `SESSION_COOKIE_FILE`, `API_ORIGIN` and `SENDER_ID` through the environment, then run:

```sh
node scripts/check-sender-release-contract.mjs
```

The script reads only the authenticated sender detail; it never changes mail. It refuses redirects so credentials cannot follow a moved URL. It prints only the contract name, pass verdict and elapsed time; no cookie, sender ID, response body or mailbox counts. Missing session, missing sender, auth errors, missing fields, noninteger/negative/null counts or unreachable API return exit 1 with `UNVERIFIED`. Delete the session file after use. A 200 health check or unauthenticated 401 cannot replace this contract smoke. Finish with an authenticated browser check that the actual UI shows counts and permits normal sender switching.

Validation: 10 Node script tests passed, including the missing-field regression, absent/unreachable-source negative controls, privacy of output, and connection release on probe failure; ESLint and formatting passed. The production authenticated script has not been run in this worktree because no controlled session cookie file was provided. No production deployment, capacity change, region move, or release promotion was performed.
