## QA-triage-20260827-01 — queue `ORDER BY` is not a total order

- **Symptom** — which 12 senders appear in Triage is undefined; any write to
  `triage_decisions` reshuffles order _and_ membership under the reader.
- **Observed** — after expanding two cards, five untouched rows reshuffled at
  unchanged confidence (Temu #7→#1, Victoria's Secret #6→#3, Donna Wilson #4→#6);
  Classic Firearms went #2→#12.
- **Cause** — `apps/api/src/triage/triage.read-service.ts:301`,
  `case 'actionable': return null`. The daily route takes the null-goal branch, so
  ordering is `[verdictPriority, desc(confidence)]` with **no tiebreak**. The
  `senderKey` tiebreak in the array literal is on the goal-priority (onboarding)
  branch and never runs on `/triage`.
- **Measured** — 6 decisions tie at `unsubscribe/0.91`, 2 at `0.89`, **33 at
  `0.87`** for the last 4 of 12 `LIMIT` slots.
- **Fix** — add a stable tiebreak on the actionable path; `senderKey` matches the
  onboarding branch so the two converge. Do **not** throttle the re-score — that
  is D25, a sanctioned founder decision, and not the bug.
- **Refuter's surviving objection** — the pre-re-score confidence no longer exists
  (`onConflictDoUpdate`, no history table), so "a confidence change caused the
  move" was never proven; a verdict flip ranks ahead of confidence and produces
  the identical movement. The fix must therefore stabilise the order regardless
  of which column changed — which a total order does.
- **Regression test** — `apps/api/src/triage/triage.read-service.spec.ts`. Seed ≥3
  decisions tied on verdict _and_ confidence, page twice with an unrelated write
  between, assert identical sender order. Negative control required.

## QA-triage-20260827-02 — "LAST SEEN today" false for 89% of rows asserting recency

- **Symptom** — tile reads "today" for a sender whose newest message is up to 89
  days old; one card read "today" for a sender last seen 2026-07-13 (45 days).
- **Cause** — `triage.read-service.ts:541` projects `sql<Date | null>` over
  `MAX(internal_date)`. Drizzle applies no decoder to a raw `sql` fragment
  (`SQL.decoder` = `noopDecoder`), so the value arrives as a **string**. At ~:603
  the `??` selects that non-null string and shadows `r.lastSeenAt`, which _is_ a
  correct `Date`; `instanceof Date` is false and the `: 0` branch renders "today".
- **Runtime proof** — instrumented live process, since reverted:
  `aggType:"string"`, `aggCtor:"String"`, `lastSeenCtor:"Date"`, `chosenIsDate:false`.
- **Measured** — of 8,051 queue-eligible senders, 954 assert a day-value and
  **849 (89%) are wrong**. The FE guard `lastSeenLabel`
  (`apps/web/src/features/triage/data.ts:1076`) is gated on
  `last90dMessages === 0`, so it rescues only the 7,097 quiet senders — the cases
  where "today" would be self-evidently absurd — and never covers the 1–89 day band.
- **Fix, both halves** — (a) make the value honest: coerce, select the typed
  column, or declare `sql<unknown>` and normalise;
  `packages/workers/src/lapse-reengagement.worker.ts:251` is the repo's correct
  exemplar. (b) the `: 0` fallback is its own defect — it answers "I could not
  read this" with the most recent possible date. Unknown must propagate as
  unknown, matching this file's own rule ("no denominator means unknown, not zero").
- **Siblings — swept, do not redo** — every other raw-SQL timestamp site already
  normalises and is **not** to be touched: `undo.service.ts:281`,
  `senders.read-service.ts:576/1484/1519`, `autopilot-action.worker.ts:1352`,
  `activity.read-service.ts:370`, `lapse-reengagement.worker.ts:251`,
  `initial-sync.worker.ts:1102`, `incremental-sync.worker.ts:1000`. Triage is the
  sole holdout. The numeric half of the class is clean.
- **Bad test to fix** — `apps/web/src/features/triage/triage-row.test.tsx:189`
  asserts `lastSeenLabel({ last90dMessages: 13, lastDays: 0 })` is `'today'`: a
  green test pinning the wrong output for exactly the uncovered case.
- **Refuter's surviving objection** — blast radius is one display tile;
  `lastDays` has a single consumer (`triage-row-expanded.tsx:78`) and nothing in
  preview, mutation, undo or scoring reads it. Keep the change proportionate.
- **Why no test caught it** — the API spec suite runs on PGlite, which returns a
  real `Date`, so the defect cannot reproduce under the existing harness. Assert
  on the mapping given a **string** input.
- **Prior art** — merged PR #258 already prescribes this one-liner; open ~8 weeks.

## QA-triage-20260827-03 — "reduce future noise by ~10%" measures the past

- **Symptom** — Today panel: "12 sender decisions can reduce future noise by
  ~10%." Arithmetic verified exact (1,243 / 12,363 inbound in 90d = 10.05%). The
  sentence is what is wrong.
- **Cause** — `queuedNoise` sums `last90dMessages` over non-Keep rows
  (`triage.read-service.ts:~1071`) ÷ 90-day inbound (~:1088) — a **past** share of
  mail already received. But `packages/shared/src/actions/action-semantics.ts:169`
  (Archive) and `:194` (Later) both carry
  `futureMail: { effect: 'unchanged', summary: 'Future email is unchanged.' }`.
  Keep leaves delivery alone; Delete only trashes what already arrived.
  Unsubscribe is the only verb of five that reduces future mail, and only if the
  sender honours it. Archive all 12 and the promised ~10% reduction is in nothing.
- **Fix** — change the **sentence**, not the computation. Provisional:
  "12 decisions below. These senders sent 10% of the email you received in the
  last 90 days."
- **Constraint** — the founder flagged this string as a positioning decision in
  their voice. Wire the provisional string and mark it **PENDING FOUNDER WORDING**
  in the PR body. Do not invent alternative claims.
