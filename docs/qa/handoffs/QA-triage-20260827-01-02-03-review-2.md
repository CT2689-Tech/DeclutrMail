## Be hostile about the round-1 fixes specifically

The fixes are new code written under time pressure by the party being
reviewed. Attack them, in this order:

1. **`windowStart` threading.** `listQueue` now takes an optional
   `windowStart`. Every caller that does NOT pass one still derives its own.
   Is there a caller whose `last90dMessages` is now compared against, or
   rendered beside, a number computed from a different window? Onboarding
   calls `listQueue` too. Does the optional parameter create a second, quieter
   version of the exact bug it fixed?

2. **Dropping the clamp.** `noiseReductionPct` is now `null` when
   `queuedNoise > total`. Trace what `null` renders as, on every surface that
   reads this field — not only the Today strip. Is there a consumer for which
   `null` is worse than a wrong number, or one that treats `null` as zero?

3. **The optional wire field.** `noiseSenderCount` is now optional on the WEB
   type and still required on the API type. Is that split coherent? Find any
   other consumer, fixture, story, SSR path or cache entry where the optional
   type now permits something that was previously rejected at compile time.
   And: is `noiseSenders <= queuedDecisions` actually the right guard, or does
   it wrongly reject a legitimate state?

4. **The inbound-filtered MAX.** It returns NULL for a sender with only
   outbound rows, which now falls back to `senders.lastSeenAt`. Is that
   fallback inbound-derived on every path that writes it — initial sync,
   incremental sync, backfills? If any writer sets it from outbound mail, the
   fix moved the falsehood rather than removing it.

5. **The new tests.** For each of the four added tests, state what it would
   have to look like to pass against the OLD code. A test that cannot fail is
   the defect this repo has shipped three times.
